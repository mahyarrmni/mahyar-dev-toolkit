## ۱. این محصول چیست؟

وقتی مشتری پیام می‌دهد (از فرم سایت، ایمیل، تلگرام و...)، SupportFlow AI به‌صورت خودکار:

| مرحله | کار |
|---|---|
| **طبقه‌بندی** | نوع درخواست را تشخیص می‌دهد: مالی، فنی، حساب کاربری، ارسال، محصول، شکایت، حقوقی، امنیتی، سایر |
| **تحلیل احساس** | ناراحتی یا رضایت مشتری را با نمرهٔ ۱- تا ۱ می‌سنجد |
| **اولویت‌بندی** | اولویت را کم / متوسط / زیاد / فوری تعیین می‌کند |
| **پاسخ هوشمند (RAG)** | در پایگاه دانش **خودتان** (سیاست‌ها، سؤالات متداول، راهنماها) جست‌وجو می‌کند و فقط بر اساس همان‌ها پاسخ می‌نویسد |
| **ارجاع به انسان** | اگر موضوع حساس است یا مطمئن نیست، تیکت را با اولویت به کارشناس می‌دهد |

اجزا: **n8n** (اتوماسیون و اتصال کانال‌ها)، **FastAPI** (منطق اصلی و داشبورد)، **Ollama** (اجرای مدل زبانی محلی)، **PostgreSQL + pgvector** (دیتابیس و جست‌وجوی برداری)، **Docker** (اجرای یکپارچه).

## ۲. کاربردها

سیستم مستقل از نوع کسب‌وکار است؛ فقط پایگاه دانش را با محتوای خودتان پر می‌کنید.

- **فروشگاه اینترنتی:** وضعیت ارسال، مرجوعی، بازگشت وجه، ضمانت
- **استارتاپ و SaaS:** مشکلات فنی، بازیابی رمز، راهنمای استفاده
- **خدمات مالی و بیمه:** سؤالات متداول، پیگیری درخواست (موارد حقوقی/امنیتی همیشه به انسان می‌رود)
- **آموزش آنلاین و دانشگاه:** ثبت‌نام، شهریه، دسترسی به دوره‌ها
- **کلینیک و خدمات:** ساعات کاری، نوبت‌دهی، قوانین
- **سازمان‌ها و تیم‌های IT:** میزکار پشتیبانی داخلی

**مزایا:** پاسخ سریع ۲۴ ساعته به سؤالات تکراری، کاهش بار کارشناسان، رسیدگی سریع‌تر به مشتریان ناراضی، حفظ کامل حریم خصوصی داده‌ها و بدون هزینهٔ اشتراک.

## ۳. سیستم چطور کار می‌کند؟

```
مشتری ──► n8n (وب‌هوک) ──► FastAPI ──► Ollama (طبقه‌بندی + پاسخ)
                              │  ▲
                              ▼  │
                     PostgreSQL + pgvector (تیکت‌ها + پایگاه دانش)

ارجاع‌شده ──► n8n ──► اعلان در چت تیم ──► کارشناس در داشبورد پاسخ می‌دهد
```

مسیر یک تیکت:
1. پیام وارد می‌شود و متن آن ضدتزریق‌دستور (prompt injection) پاک‌سازی می‌شود.
2. مدل، دسته، احساس، فوریت و زبان را برمی‌گرداند و خروجی اعتبارسنجی می‌شود.
3. اولویت با **قانون ثابت** محاسبه می‌شود (نه با نظر مدل): `فوریت + (احساس خیلی منفی) + (موضوع حقوقی/امنیتی)`.
4. مرتبط‌ترین بخش‌های پایگاه دانش پیدا می‌شود.
5. اگر مطلب مرتبط کافی بود، مدل پاسخ و **درجهٔ اطمینان** می‌نویسد.
6. اگر هیچ دلیل ارجاعی نبود، پاسخ خودکار به مشتری می‌رسد؛ وگرنه تیکت وارد صف انسانی می‌شود و مشتری پیام «درخواست ثبت شد، همکاران تماس می‌گیرند» را می‌بیند.

## ۴. پیش‌نیازها

- Docker و Docker Compose نسخهٔ ۲
- ابزار `openssl` (برای ساخت رمزهای تصادفی؛ در لینوکس/مک موجود است، در ویندوز از WSL2 یا Git Bash استفاده کنید)
- حدود **۸ گیگابایت RAM آزاد** و **۸ گیگابایت فضای دیسک** (مدل‌ها حدود ۶ گیگابایت)
- کارت گرافیک اختیاری است؛ روی CPU کار می‌کند ولی هر پاسخ ممکن است چند ده ثانیه طول بکشد. برای GPU انویدیا بخش کامنت‌شدهٔ `ollama` در `docker-compose.yml` را فعال کنید.
- روی سخت‌افزار ضعیف مقدار `CHAT_MODEL=qwen2.5:3b` را در `.env` بگذارید.

## ۵. نصب و راه‌اندازی

```bash
git clone <آدرس-مخزن-شما> supportflow-ai
cd supportflow-ai

sh scripts/init-env.sh              # ساخت فایل .env با رمزهای تصادفی
docker compose up -d --build        # ساخت و اجرای همهٔ سرویس‌ها
docker compose logs -f model-init   # دنبال کردن دانلود مدل‌ها (فقط بار اول)
sh scripts/seed.sh                  # اختیاری: پایگاه دانش نمونه
```

وقتی `model-init` تمام شد (پیام پایان دانلود هر دو مدل)، سیستم آماده است. بررسی سلامت:

```bash
curl http://localhost:8000/health   # باید {"status":"ok"} بدهد
curl http://localhost:8000/ready    # بعد از دانلود مدل‌ها باید ready بدهد
```

| سرویس | آدرس |
|---|---|
| داشبورد | http://localhost:8000 |
| n8n | http://localhost:5678 |

> همهٔ پورت‌ها فقط روی `127.0.0.1` باز هستند. برای دسترسی از بیرون، پشت یک reverse proxy با HTTPS (مثل Caddy یا nginx) قرار دهید.

## ۶. آموزش گام‌به‌گام

### گام ۱ — ورود به داشبورد
آدرس http://localhost:8000 را باز کنید. مقدار `API_KEY` را از فایل `.env` کپی کنید (`grep ^API_KEY .env`) و در کادر بالای صفحه وارد کنید. کلید فقط در حافظهٔ موقت مرورگر (تا بستن تب) نگه‌داری می‌شود.

### گام ۲ — ساخت پایگاه دانش (مهم‌ترین گام)
کیفیت پاسخ‌ها مستقیم به این بخش بستگی دارد.
1. تب **پایگاه دانش** را باز کنید.
2. یک عنوان بنویسید (مثلاً «سیاست مرجوعی») و متن کامل را بچسبانید.
3. «افزودن» را بزنید. متن به بخش‌های کوچک تقسیم و برداری‌سازی می‌شود.

نکات نوشتن محتوای خوب:
- هر موضوع در یک سند جدا؛ متن شفاف و کامل (شرایط، مهلت‌ها، مبالغ، مراحل).
- پاسخ را همان‌طور بنویسید که می‌خواهید مشتری بشنود.
- سندهای قدیمی را حذف و نسخهٔ جدید را اضافه کنید.

### گام ۳ — آزمایش با تیکت نمونه
تب **تیکت آزمایشی** را باز کنید، موضوع و متن پیام بنویسید و «ارسال» بزنید. نتیجه شامل دسته، احساس، اولویت، وضعیت، دلیل ارجاع (اگر باشد) و «پاسخ ارسالی به مشتری» است.

چند آزمایش پیشنهادی:
- یک سؤال که در پایگاه دانش هست ← باید `پاسخ خودکار` شود.
- سؤالی که در پایگاه دانش نیست ← ارجاع با دلیل `no_kb_match`.
- «با اپراتور صحبت کنم» ← ارجاع با دلیل `human_requested`.
- پیام خشمگین یا فوری ← اولویت بالا و ارجاع.

### گام ۴ — کار با صف ارجاع (برای کارشناسان)
تب **صف ارجاع** تیکت‌های نیازمند انسان را به ترتیب اولویت (فوری‌ترین بالا) نشان می‌دهد. برای هر تیکت:
- دلیل ارجاع و پیش‌نویس هوش مصنوعی (در صورت وجود) را ببینید.
- پاسخ نهایی را در کادر ویرایش و «ارسال و بستن» را بزنید. وضعیت به «حل‌شده» تغییر می‌کند.

> ارسال خودِ پاسخ به مشتری (ایمیل، تلگرام...) بر عهدهٔ n8n یا سیستم شماست؛ داشبورد پاسخ را ثبت می‌کند. برای خودکارسازی آن به بخش بعد مراجعه کنید.

### گام ۵ — پایش
کارت‌های بالای داشبورد: تعداد کل تیکت‌ها، درصد حل خودکار، تعداد در صف ارجاع و تعداد پیام‌های با احساس منفی. تب **همه تیکت‌ها** تاریخچه را نشان می‌دهد.

## ۷. اتصال به n8n

### ورک‌فلوهای آماده
در `n8n/workflows/` دو ورک‌فلو آماده است:

| فایل | عملکرد |
|---|---|
| `ticket-intake.json` | وب‌هوک دریافت تیکت ← بررسی رمز وب‌هوک ← ثبت و تحلیل در API ← اعلان برای تیکت ارجاعی ← بازگرداندن پاسخ |
| `sla-reminder.json` | هر ۱۵ دقیقه تیکت‌های فوری/زیاد بدون پاسخ بیش از ۱ ساعت را به تیم یادآوری می‌کند |

### نصب ورک‌فلوها
1. در http://localhost:5678 حساب مدیر n8n را بسازید.
2. ایمپورت:
   ```bash
   docker compose exec n8n n8n import:workflow --separate --input=/workflows
   ```
3. هر ورک‌فلو را باز و **Active** کنید (اگر ایمپورت با دستور ممکن نبود، از منوی Import from File در n8n استفاده کنید).

### ارسال تیکت از سایت یا هر سیستم دیگر
```bash
curl -X POST http://localhost:5678/webhook/support-ticket \
  -H "x-webhook-secret: <WEBHOOK_SECRET از .env>" \
  -H "Content-Type: application/json" \
  -d '{"customer":"علی","subject":"بازگشت وجه","body":"چطور پولم را پس بگیرم؟"}'
```
پاسخ: `{"ticket_id":..., "status":"auto_resolved|escalated", "reply":"..."}`. 
تا زمانی که ورک‌فلو فعال نشده، از آدرس تست `/webhook-test/support-ticket` استفاده کنید.

> رمز وب‌هوک را در جاوااسکریپت سمت کاربر (مرورگر) قرار ندهید؛ فرم سایت باید از سرور شما به وب‌هوک درخواست بفرستد.

### اعلان تیم
در `.env` مقدار `ESCALATION_WEBHOOK_URL` را با آدرس Incoming Webhook سازگار با Slack یا Mattermost پر کنید و `docker compose up -d` بزنید. بدون آن، ورک‌فلو بدون خطا ادامه می‌دهد و فقط اعلان ارسال نمی‌شود.

### افزودن کانال‌های جدید (ایمیل، تلگرام و...)
n8n نودهای آماده دارد. الگو برای هر کانال:
1. نود تریگر کانال (مثلاً **Email Trigger (IMAP)** یا **Telegram Trigger**).
2. نود **HTTP Request** به `http://api:8000/api/tickets` با هدر `X-API-Key` و بدنهٔ `{subject, body, customer}` (مانند نود *Create Ticket* در ورک‌فلو آماده).
3. نود ارسال پاسخ همان کانال با فیلد `customer_reply` خروجی.

## ۸. قوانین ارجاع به انسان

تیکت در هر یک از این حالت‌ها به انسان می‌رود (می‌توانند هم‌زمان باشند):

| کد دلیل | معنی |
|---|---|
| `sensitive_category:legal/security` | موضوع حقوقی یا امنیتی؛ هرگز پاسخ خودکار داده نمی‌شود |
| `urgent_priority` | اولویت فوری |
| `very_negative_sentiment` | مشتری بسیار ناراضی (نمرهٔ ۰٫۷- یا کمتر) |
| `human_requested` | مشتری صراحتاً اپراتور/انسان خواسته |
| `no_kb_match` | مطلب مرتبطی در پایگاه دانش نبود |
| `low_confidence` | اطمینان مدل از پاسخ پایین بود (پیش‌نویس برای کارشناس ذخیره می‌شود) |
| `ai_error` | مدل یا دیتابیس در دسترس نبود؛ برای جلوگیری از گم شدن تیکت به انسان می‌رود |

## ۹. تنظیمات

همه در فایل `.env`؛ پس از تغییر، `docker compose up -d` را اجرا کنید.

| متغیر | پیش‌فرض | توضیح |
|---|---|---|
| `CHAT_MODEL` | `qwen2.5:7b` | مدل گفت‌وگو؛ هر مدل Ollama قابل استفاده است |
| `EMBED_MODEL` | `bge-m3` | مدل امبدینگ چندزبانه (۱۰۲۴ بعدی). تغییر به مدل با ابعاد دیگر نیازمند ویرایش `db/init.sql` و ساخت مجدد دیتابیس است |
| `DEFAULT_LANGUAGE` | `fa` | زبان پیش‌فرض پیام‌های ثابت |
| `RAG_MIN_SIMILARITY` | `0.5` | حداقل شباهت برای پاسخ‌دهی؛ بالاتر = محتاط‌تر و ارجاع بیشتر |
| `ESCALATION_CONFIDENCE` | `0.6` | حداقل اطمینان مدل برای پاسخ خودکار |
| `RATE_LIMIT_PER_MIN` | `120` | سقف درخواست در دقیقه برای هر IP |
| `APP_ENV` | `production` | حالت `development` مستندات `/docs` را فعال می‌کند |
| `ESCALATION_WEBHOOK_URL` | خالی | آدرس اعلان تیم |
| `N8N_VERSION` | `latest` | برای production یک نسخهٔ مشخص بگذارید |

راهنمای تنظیم دقت: اگر پاسخ‌های خودکار غلط یا شلخته بودند، `RAG_MIN_SIMILARITY` و `ESCALATION_CONFIDENCE` را بالا ببرید و پایگاه دانش را کامل‌تر کنید. اگر ارجاع‌ها بیش از حد زیاد است، ابتدا محتوای دانش را بهتر کنید و سپس آستانه‌ها را کمی پایین بیاورید.

## ۱۰. مرجع API

همهٔ مسیرهای `/api` هدر `X-API-Key` می‌خواهند.

| متد | مسیر | کار |
|---|---|---|
| POST | `/api/tickets` | ثبت و تحلیل تیکت؛ `customer_reply` را برمی‌گرداند |
| GET | `/api/tickets?status=&limit=&offset=` | فهرست تیکت‌ها (`status`: `auto_resolved`, `escalated`, `resolved`) |
| GET | `/api/tickets/{id}` | جزئیات تیکت |
| POST | `/api/tickets/{id}/resolve` | ثبت پاسخ انسانی `{"reply": "..."}` و بستن |
| GET | `/api/stats` | آمار |
| GET/POST | `/api/kb` | فهرست / افزودن سند `{"title","content"}` |
| DELETE | `/api/kb/{id}` | حذف سند |
| GET | `/health` ، `/ready` | سلامت (بدون کلید) |

نمونه:
```bash
curl -X POST http://localhost:8000/api/tickets \
  -H "X-API-Key: $(grep ^API_KEY .env | cut -d= -f2)" -H "Content-Type: application/json" \
  -d '{"subject":"رمز عبور","body":"رمزم را فراموش کرده‌ام"}'
```

## ۱۱. امنیت

- همهٔ رمزها تصادفی ساخته می‌شوند و فقط در `.env` (خارج از گیت) هستند.
- حالت production اجازهٔ اجرا با `API_KEY` ضعیف (کمتر از ۲۴ نویسه) را نمی‌دهد.
- احراز هویت با کلید API، محدودیت نرخ درخواست، اعتبارسنجی سخت‌گیرانهٔ ورودی و کوئری‌های پارامتری (ضد SQL Injection).
- متن مشتری و پایگاه دانش در پرامپت «داده نامعتبر» تلقی می‌شود و خروجی مدل اعتبارسنجی می‌شود.
- داشبورد با CSP سخت‌گیرانه و بدون `innerHTML` (ضد XSS).
- کانتینر API با کاربر غیر root اجرا می‌شود؛ پورت‌ها فقط محلی هستند.
- n8n تله‌متری و اعلان نسخه را غیرفعال دارد.
- قبل از انتشار روی اینترنت: HTTPS، فایروال و `N8N_SECURE_COOKIE=true`.

## ۱۲. نگهداری

```bash
# پشتیبان‌گیری از دیتابیس
docker compose exec -T postgres pg_dump -U supportflow supportflow > backup.sql
# بازیابی (روی دیتابیس خالی)
docker compose exec -T postgres psql -U supportflow supportflow < backup.sql

# به‌روزرسانی کد
git pull && docker compose up -d --build

# مشاهدهٔ لاگ‌ها
docker compose logs -f api

# توقف (داده‌ها می‌مانند)
docker compose down
# توقف و حذف کامل داده‌ها ⚠️
docker compose down -v
```
از پوشهٔ `n8n` (volume) و فایل `.env` نیز نسخهٔ پشتیبان نگه دارید؛ بدون `N8N_ENCRYPTION_KEY` اطلاعات رمزگذاری‌شدهٔ n8n قابل بازیابی نیست.

## ۱۳. عیب‌یابی

| مشکل | علت و راه‌حل |
|---|---|
| همهٔ تیکت‌ها با `ai_error` ارجاع می‌شوند | مدل‌ها هنوز دانلود نشده‌اند یا Ollama بالا نیست: `docker compose logs model-init` و `curl localhost:8000/ready` |
| پاسخ‌ها خیلی کند است | اجرا روی CPU؛ از `qwen2.5:3b` یا GPU استفاده کنید |
| همیشه `no_kb_match` | پایگاه دانش خالی یا نامرتبط است؛ محتوا اضافه کنید یا `RAG_MIN_SIMILARITY` را کمی پایین بیاورید |
| خطای ۴۰۱ در داشبورد/API | کلید اشتباه است؛ مقدار `API_KEY` را از `.env` بردارید |
| خطای ۴۲۹ | سقف نرخ درخواست؛ `RATE_LIMIT_PER_MIN` را زیاد کنید |
| وب‌هوک n8n خطای ۴۰۴ می‌دهد | ورک‌فلو فعال نیست؛ آن را Active کنید یا از `/webhook-test/` استفاده کنید |
| وب‌هوک ۴۰۱ می‌دهد | هدر `x-webhook-secret` با `WEBHOOK_SECRET` یکی نیست |
| `docker compose` دربارهٔ متغیر خالی خطا می‌دهد | `.env` ساخته نشده؛ `sh scripts/init-env.sh` را اجرا کنید |
| پورت ۸۰۰۰ یا ۵۶۷۸ اشغال است | پورت‌ها را در `docker-compose.yml` تغییر دهید |
| API بالا نمی‌آید و می‌گوید `Set a strong API_KEY` | کلید ضعیف است؛ با `init-env.sh` فایل جدید بسازید |

## ۱۴. پرسش‌های متداول و محدودیت‌ها

**آیا داده‌ها از سرور من خارج می‌شوند؟** خیر. مدل‌ها محلی اجرا می‌شوند. فقط دانلود اولیهٔ مدل‌ها و ایمیج‌های Docker به اینترنت نیاز دارد.

**آیا مدل ممکن است اشتباه کند؟** بله. به همین دلیل موارد حساس و کم‌اطمینان همیشه به انسان می‌روند. پاسخ‌های خودکار را در ابتدا از تب «همه تیکت‌ها» بازبینی کنید و پایگاه دانش را مرتب بهبود دهید.

**چند زبان؟** زبان پیام تشخیص داده می‌شود و پاسخ به همان زبان نوشته می‌شود؛ پیام تأیید ثابت فقط برای فارسی و انگلیسی تعریف شده است (`ACK` در `backend/app/pipeline.py`).

**محدودیت‌های فعلی:**
- ارسال پاسخ نهایی کارشناس به کانال مشتری خودکار نیست و باید در n8n ساخته شود.
- محدودیت نرخ درخواست داخل حافظهٔ یک پروسه است (برای چند نمونهٔ API از reverse proxy استفاده کنید).
- ساختار دیتابیس فقط در اولین اجرا ساخته می‌شود؛ برای تغییرات بعدی ابزار migration اضافه کنید.
- نقش‌های چندکاربره در داشبورد وجود ندارد؛ یک کلید API مشترک است.
